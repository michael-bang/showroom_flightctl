. `Edge Manager Agent`: The device agent uses a pull-based architecture to retrieve configuration and updates, which is well suited for edge environments where inbound connectivity may be limited or not allowed

. `Enrollment Configuration`: This configuration file contains the information required for the device to enroll and authenticate with Edge Manager

=== Edge Manager Agent

The Edge manager agent is implemented in pull mode. This means that Edge Manager does not connect to the device, but the Edge manager agent connects to the Edge Manager.

The Edge manager agent is responsible for:

. `Pulls Down Desired Configurations:` It checks in with the central service, asks, "How should this device be configured right now?", 
and automatically updates the machine’s operating system and apps to match that target state.  
. `Handles Safe, Reliable Updates:` When operating system or app updates are ready, the agent downloads everything safely in the background. 
If a network connection drops mid-download, it recovers gracefully, and if an update fails to boot, it can roll back to the previous working state automatically.
. `Reports Health and Status:` It continuously monitors the machine's vitals (is it online? are the containers running? did the update succeed?) and reports progress 
back to the main control panel.  
. `Enrolls Devices Securely:` When a new machine turns on for the first time, the Agent handles the cryptographic "handshake" to securely register the device to your fleet.
Essentially, it acts as the on-device "worker" that executes your fleet commands locally, making sure the device stays up to date and healthy even in unreliable network
 environments.

Edge Manager can currently manage devices that is running an Image Mode / Bootc based Operating System. These can be based on a number of different Linux based distributions.

=== Enrollment Configuration
The enrollment configuration is a set of files that the Edge manager agent uses to connect to the Edge Manager in a secure way. The enrollment configuration can be
baked into the image so that every instance created from that instance knows exactly which Edge Manager to connect. If the instance is running virtual on a Hypervisor like
 OpenShift Virtualization and support cloudinit then it is possible to do a late binding of the configuration. 

== Edge Manager Fleets

An Edge Manager fleet is a logical grouping of devices that share a common *desired state* and management policies. Fleets simplify large-scale operations by allowing administrators to define a single *fleet specification* that applies consistently across all devices in the group. This specification can include applications, host configuration, and OS image references, ensuring predictable behavior and updates across the fleet.

NOTE: A device can belong to at most one fleet at a time. This design avoids configuration conflicts and ensures each device has a single, authoritative source of truth for its desired state.

image::m1-fleet-definition-2.png[link=self, window=blank, width=100%]

Fleets provide centralized, template-driven management for groups of edge devices. Without centralized management, each device must be updated, monitored, and managed individually (an approach that is time-consuming and prone to inconsistency). 

With Edge Manager fleet management, a single fleet template defines the desired application set, host configuration and OS image for all member devices. This enables administrators to apply updates consistently, enforce configuration, and monitor fleet-wide health from a single point of control. Fleet status views summarize how many devices are healthy, updating, or in a failed state, enabling quick operational insight.

=== Onboard a device

. Go to the *Devices* page

You will see a page like the following.

image::m1-device-list.png[link=self, window=blank, width=100%]

. Click on the *edgesrv2* device that are ready to be approved.

Here you can see information about the device that is ready to be imported. You can see the host name, ip address, the distribution and other information about the device. 

image::m1-edgesrv2-device-info.png[link=self, window=blank, width=100%]

From here you can approve the device which will import the device into Edge Manager so you can manage the device.
You can also reject the device if you don't want to allow the device into Edge Manager.

. Click on the *Actions* drop down button

. And click *Approve*

image::m1-approve-device.png[link=self, window=blank, width=100%]

On the *Approve pending device* screen you can give the device an alias. The alias is the name you will see in Edge Manager.
The alias is prefilled with the devices host name.  

When you approve the device you can add labels to the device.
These labels can be used to a number of things. You could for instance add a geo based label like geo=EMEA or city=copenhagen. This will make it easier to find devices that are
located in same area. 
Labels can also be used to make a device part of a fleet. There is also a third feature you can use labels for and we will look further at this in module 2.

We will add this device to a fleet in the next module, but for now we just want to import it into Edge Manager.

. Click approve

The *edgesrv2* device has now been enrolled into the Edge Manager and you will be presented with a screen where you can see information about the device.

image::m1-edgesrv2.png[link=self, window=blank, width=100%]

In the *System status* you can see that the device is *up-to-date* and that the device is *Online*. It might take a little bit of time before this is the case for you. 
This is because the agent need to be aware of the enrollment and provide status information back to the Edge Manager. 

You have now successfully added your first device to Edge Manager.
